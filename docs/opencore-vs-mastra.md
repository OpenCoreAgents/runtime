# OpenCore Agents and Mastra

OpenCore Agents gives application teams control over where their agent runtime runs and how it dispatches work. Its strongest differentiators in this review are on-device inference in a browser and a planner that can create a subagent definition and dispatch it as a background job. Mastra offers more integrated tooling for typed workflows, agent versioning, observability, and evaluation.

Reviewed November 20, 2026. The OpenCore baseline is the [`dev` merge of PR #24](https://github.com/OpenCoreAgents/runtime/commit/97ccf912b91ec7050c14333c87c9bcfd6dda0791), which includes the Redis approval and browser test fixes. The [OpenCore documentation site](https://opencoreagents.github.io/runtime/) is cited separately for its published integration examples. Mastra evidence comes from its official documentation. The scorecard describes documented capabilities and integration effort across both projects.

## Policy pipeline integration

The SDK exposes a tool visibility policy and a pre-execution policy that evaluates canonical arguments and can allow, deny, or suspend a call for approval. The SDK can approve, reject, or cancel a pending action, and it evaluates the policy again at approval time. It also exposes versioned public events with a configurable redactor and event sinks. [Visibility policy](../packages/core/src/engine/toolVisibilityPolicy.ts) · [Execution policy](../packages/core/src/engine/executionPolicy.ts) · [Approval API](../packages/core/src/engine/approvalApi.ts) · [Public events](../packages/core/src/engine/publicEvents.ts)

Approval currently requires an approval-capable run store. The in-memory store and `RedisRunStore` implement the pending-action claim. The reference Redis/BullMQ app still needs authenticated HTTP approval wiring. Its SSE interface continues to use the separate Redis lifecycle hooks. [Run store contract](../packages/core/src/adapters/run/RunStore.ts) · [In-memory store](../packages/core/src/adapters/run/InMemoryRunStore.ts) · [Redis run store](../packages/adapters-redis/src/RedisRunStore.ts) · [Runtime server](../apps/runtime/src/server.ts)

## Verification results

OpenCore’s browser example wires WebLLM and IndexedDB. Its planner writes the subagent definition before calling the queue. The merged changes fix the browser compatibility test, add atomic Redis claims, and preserve pending approvals when a caller attempts an ordinary resume. [Browser example](../examples/browser-local/src/main.ts) · [Planner source](../packages/dynamic-planner/src/registerDynamicPlannerTools.ts) · [PR #24](https://github.com/OpenCoreAgents/runtime/pull/24)

The Redis regression test and a check with two clients on a local Redis server confirmed that one claim wins and the prepared input keeps its JSON shape. The BullMQ integration test and the browser example build also passed. The reference app still needs an authenticated HTTP approval flow. Live WebGPU inference, Mastra deployment, and cross-process crash recovery were outside the hands-on review. [Browser compatibility test](../packages/core/tests/browser-compat.test.ts) · [Redis tests](../packages/adapters-redis/tests/redis-adapters.test.ts) · [Approval tests](../packages/core/tests/approvalApi.test.ts)

## Scorecard

This scorecard gives each of the twelve capability areas equal weight. Each area is scored from 0 to 5. A 0 means the review found no relevant evidence, 1 means only adjacent capabilities were documented, 2 means basic primitives are available, 3 means the core capability is available with significant integration work, 4 means a usable implementation covers most of the area, and 5 means the reviewed materials show a complete path for the capability as defined in this comparison. The total is the sum divided by 60, multiplied by 100 and rounded to one decimal place.

| Area | OpenCore Agents | Mastra | Scoring rationale |
| --- | ---: | ---: | --- |
| Execution and deployment | 4 | 5 | OpenCore ships a reference queue-and-worker stack. Mastra adds typed workflow graphs, recovery controls, and a managed deployment option. |
| On-device browser runtime | 4 | 1 | OpenCore provides browser-local orchestration and persistence, with a WebGPU inference path in the example. The local bundle and adapter tests pass. Live WebGPU inference remains unverified. Mastra documents browser automation and a client for server-side agents. |
| Multi-agent orchestration | 4 | 4 | OpenCore integrates definition creation and queue dispatch. Mastra provides several delegation patterns, asynchronous tools, and stored-agent APIs. |
| Dynamic definitions | 4 | 5 | OpenCore hydrates Redis definitions at execution time. Mastra also documents drafts, publishing, and per-request version selection. |
| Ready-made adapters | 4 | 5 | OpenCore provides explicit runtime contracts and concrete adapters for the reference stack. Mastra documents a wider selection of model providers, storage backends, and server frameworks. |
| Custom adapters | 5 | 4 | This criterion measures how directly an application can replace core runtime dependencies. OpenCore exposes separate interfaces for model calls, memory, run snapshots, and messaging. Mastra exposes custom gateways, storage domains, server adapters, and signal providers. Its documented extension points follow those component contracts, with feature-specific requirements such as Observational Memory support. |
| Multi-tenancy | 4 | 4 | OpenCore provides project and tenant scoping with host-managed membership and authentication. Mastra provides thread ownership and stored-agent visibility with application-managed tenant identity and membership. |
| Tools and governance | 3 | 4 | OpenCore supports approval in the SDK and atomic Redis claims. The reference app still requires HTTP approval wiring. Mastra documents approval and suspension with persistent storage and configurable permissions. |
| Memory, retrieval, and skills | 4 | 4 | OpenCore provides RAG ingestion and OpenClaw loading. Mastra provides integrated memory, semantic recall, and workspace skills. |
| API and developer tooling | 3 | 5 | OpenCore has a reference API, playground, CLI, and an application-level MCP example. Mastra integrates Studio, REST, typed signals, and dedicated MCP components. |
| Conversation gateway and channels | 3 | 4 | OpenCore provides reusable run/resume and reply routing, with production transport and delivery behavior supplied by the host. Mastra documents packaged channel providers and controller-level webhook and session routing. |
| Observability and evaluation | 2 | 5 | OpenCore exposes history, usage, and events. Mastra provides trace inspection, datasets, scorers, and experiments. |
| **Total** | **73.3/100** | **83.3/100** | **44/60 for OpenCore Agents and 50/60 for Mastra.** |

## Production use without an enterprise agreement

OpenCore publishes the runtime under Apache 2.0. Mastra also offers its open-source framework under Apache 2.0. Mastra Enterprise features, including code in `ee/` directories, require a written agreement that expressly permits the intended production use and a valid license key under the published Enterprise terms. Managed platform services have their own terms. For a deployment without an Enterprise agreement, verify the license and availability of each required component before applying the scorecard. [OpenCore license](https://github.com/OpenCoreAgents/runtime/blob/main/LICENSE) · [Mastra license mapping](https://github.com/mastra-ai/mastra/blob/main/LICENSE.md) · [Mastra Enterprise license](https://github.com/mastra-ai/mastra/blob/main/ee/LICENSE)

## Implications

OpenCore is a strong fit when the product needs on-device inference, subagents assembled at runtime, or direct ownership of a Redis and BullMQ execution stack. Its project and tenant identifiers give a host application inputs for scoping runs. The host still owns identity mapping and authorization, and it must account for retries and idempotency when tools have external effects. [Production considerations](roadmap/technical-debt-security-production.md)

Mastra is a strong fit when the team needs typed workflows, agent revision management, and an integrated workflow for inspecting and evaluating agents. For an existing OpenCore deployment, the most informative migration test would use a representative project with dynamic subagent creation, a long-running tool with side effects, and a pause followed by a process restart. Check run identity, definition revision, tenant boundaries, and tool behavior under retry in both systems.
