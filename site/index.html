Build agent APIs and background workers.

OpenCore Agents is a TypeScript runtime for running agents in your Node.js application or dispatching work to a queue. Persist runs so they can resume, and let a planner define and queue subagents as work comes in.

Run the example Read the engine reference </> View code

Run lifecycle

  1. RunLoad an agent into a session and send input.
  2. ActExecute a tool and pass its result back to the model.
  3. Wait and resumePause for input and continue with the same run ID.
  4. CompleteReturn a result and retain the run history.

Why OpenCore Agents

Move long-running work out of HTTP requests

The reference Express API can return a job ID while BullMQ workers execute the run. Read progress from the run API, or enable server-sent events to stream updates.

Read the API and event guide

Create and queue subagents at runtime

A planner can give a new subagent instructions, tools, and a model, persist its definition, and enqueue its run. It can then wait for the result and use it in the parent run.

See how delegation works

Update agents without redeploying workers

Store prompts, skills, and HTTP tool configuration by project in Redis. Workers load the definitions when they pick up a job, so edits can take effect on the next run.

Build a custom adapter

Build with the TypeScript SDK

Define an agent and start a run

In the minimal example, a scripted model and in-memory adapter make the run reproducible. The session and agent definition share a project ID.

const runtime = new AgentRuntime({
  llmAdapter: new DeterministicDemoLlm(),
  memoryAdapter: new InMemoryMemoryAdapter(),
});

await Agent.define({
  id: "demo-greeter",
  projectId: "demo-project",
  systemPrompt: "You are a helpful assistant.",
  tools: [],
  llm: { provider: "openai", model: "gpt-4o-mini" },
});

const session = new Session({
  id: "demo-session-1",
  projectId: "demo-project",
});
const agent = await Agent.load("demo-greeter", runtime, { session });
const run = await agent.run("Say hello.");

Pause for input and resume by run ID

In the support example, the agent asks for an email address before opening a ticket. The application resumes the waiting run after it receives the answer.

let run = await agent.run(refundMessage);

if (run.status === "waiting") {
  const resumeText = await readUserResumeMessageAsEmail(ticketEmailRef);
  run = await agent.resume(run.runId, {
    type: "text",
    content: resumeText,
  });
}

Configure a shared RunStore to resume from another process. Use agent.continueRun(runId, message) to append a new turn to a completed or failed run.

Deploy an API and background workers

  1. Express accepts POST /agents/:agentId/run and queues the run in BullMQ.
  2. BullMQ delivers the job to a separate worker process.
  3. The worker can load definitions from Redis, execute the run, and persist state in the shared RunStore.

Use GET /jobs/:jobId to check the queue and GET /runs/:runId?sessionId=… to read the run. The runtime can also stream run events when SSE is enabled.

How dynamic agents and subagents work

Define a reusable agent by saving its prompt, tools, and model under a project in Redis. When BullMQ hands a job to a worker, the worker loads the agent and its referenced skills and HTTP tools before running it.

The worker reads the definitions when it processes each job, so updates can also affect jobs that are already queued.

await store.Agent.define({
  id: "support-agent",
  projectId: "support",
  systemPrompt: "Help customers with their orders.",
  tools: [],
  llm: { provider: "openai", model: "gpt-4o-mini" },
});

Example: investigate a support ticket

  1. Delegate in the backgroundThe support agent calls invoke_planner and receives a run ID it can check later.
  2. Define two specialistsThe planner uses spawn_agent to assign an order lookup and a policy review. Each subagent gets its own instructions, tools, and run ID. The definition is stored in Redis before the run is queued.
  3. Collect the resultsWorkers run the specialists. The planner calls wait_for_agents with their run IDs to collect results or failures from a shared RunStore.
  4. Return to the conversationIn the reference chat app, a later turn in the same session can fetch the planner result with runtime_fetch_run.

Run agents for multiple tenants

Share agent definitions across customers in one project and scope runs by tenant. Use separate projects when customers need separate agent, skill, and tool definitions.

  • projectId selects the agent definition namespace.
  • tenantId adds a run scope within that project.
  • Session.id identifies the conversation or workflow.

Bind the session to an authorized tenant

Resolve these IDs on the server after authenticating the caller and checking access to the project, tenant, and conversation.

const session = new Session({
  id: conversation.id,
  projectId: access.projectId,
  tenantId: access.tenantId,
});

const agent = await Agent.load("support-agent", runtime, {
  session,
});
const run = await agent.run(message);

Bring your own adapters

Implement the SDK interfaces and pass your implementations to AgentRuntime. Agent definitions and run calls can stay the same while you change providers or infrastructure.

  • LLMAdapter connects a model provider or internal gateway. Use llmAdaptersByProvider to route agents by provider.
  • MemoryAdapter stores conversation memory. RunStore persists run state for later resume.
  • MessageBus transports messages between agents.

Read the adapter contracts

Inject a model adapter

This adapter returns a fixed protocol result for local tests. For a real provider, implement generate(request) to translate the request and map the provider response to LLMResponse.

import {
  AgentRuntime,
  InMemoryMemoryAdapter,
  type LLMAdapter,
} from "@opencoreagents/core";

const llmAdapter: LLMAdapter = {
  async generate() {
    return {
      content: JSON.stringify({
        type: "result",
        content: "Hello from a custom adapter.",
      }),
    };
  },
};

const runtime = new AgentRuntime({
  llmAdapter,
  memoryAdapter: new InMemoryMemoryAdapter(),
});

Build an agent with RAG

Give an agent a project-scoped catalog of documents, then use retrieval-augmented generation (RAG) to find relevant passages for its answer.

  1. Register sources. Give each document an ID and description. Configure fileReadRoot on the runtime so relative paths resolve to your documents.
  2. Ingest documents. system_ingest_rag_source reads the source by catalog ID, chunks it, generates embeddings, and writes them to the vector store.
  3. Retrieve passages. system_vector_search returns relevant chunks as a tool result for the agent's next step.
Read the RAG guide

Connect agents to your HTTP APIs

Define an outbound HTTP call as configuration. Attach the tool to an agent to look up order status, read account data, or hand off work to a ticketing API.

  • Describe the input with a JSON schema and use templates to map arguments to the request.
  • Keep credentials separate from the definition and restrict the request to approved hosts with allowedHosts.
  • Store definitions in Redis when workers need to load updated integrations per job.

Read the HTTP tool reference

Register an order lookup tool

import { registerHttpToolsFromDefinitions }
  from "@opencoreagents/adapters-http-tool";

await registerHttpToolsFromDefinitions(
  [{
    id: "lookup_order",
    projectId: "support",
    description: "Look up an order by ID.",
    inputSchema: {
      type: "object",
      properties: { orderId: { type: "string" } },
      required: ["orderId"],
    },
    http: {
      method: "GET",
      url: "https://orders.example.com/v1/orders",
      allowedHosts: ["orders.example.com"],
      query: { id: "{{input.orderId}}" },
      headers: {
        authorization: "Bearer {{secret:ORDERS_API_KEY}}",
      },
    },
  }],
  { secrets: { ORDERS_API_KEY: ordersApiKey } },
);

Pass ordersApiKey from your application's secret store. Add tools: ["lookup_order"] to the agent definition in the support project.

Select the tools an agent can call

In this example, registerMcpTools is an application helper and client is already connected.

const toolIds = await registerMcpTools(
  client,
  projectId,
  "orders",
  ["lookup_order", "estimate_delivery"],
);

await Agent.define({
  ...agentDefinition,
  projectId,
  tools: toolIds,
});

Core tool IDs are derived from the project, connection namespace, and remote tool name. Give each connection in a project a distinct namespace. The helper rejects IDs already registered in the process.

Pass "*" as the last argument to register the entire server catalog. Use an explicit list to give an agent access to specific tools.

Configure memory and secrets

  • Memory. Start with InMemoryMemoryAdapter for a single process or use RedisMemoryAdapter to share memory between workers. Memory keys depend on the adapter and the scope passed to it.
  • Run state. Use RedisRunStore to persist run history and resume a waiting run from another worker.
  • Secrets. Put a reference like {{secret:ORDERS_API_KEY}} in the HTTP tool definition. Resolve the value from your application's secret store when the runtime loads dynamic definitions. Keep secret values out of definitions and queue payloads.

Read the memory and run-store contracts

Wire shared state and tool credentials

const runtime = new AgentRuntime({
  llmAdapter,
  memoryAdapter: new RedisMemoryAdapter(redis),
  runStore: new RedisRunStore(redis),
  dynamicDefinitionsStore: definitionsStore,
  dynamicDefinitionsSecrets: () => ({
    ORDERS_API_KEY: ordersApiKey,
  }),
});

ordersApiKey comes from the worker's configuration. If your API also hydrates those definitions, configure the credential there too.
